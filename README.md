### 1. Оптимизация витрины

#### 1.1. Два запроса и исходное измерение
**Узкий запрос:** июнь 2023 (~4% данных, ~20 000 строк)  
**Широкий запрос:** весь период 2022-2023 (100% данных, 500 000 строк)

Перед измерениями выполнена команда `ANALYZE large.orders` для обновления статистики.

**Результаты (медиана из 5 повторов после прогрева):**

| Вариант | Узкий (мс) | Широкий (мс) |
|---------|-----------|--------------|
| Исходная (без индекса) | 13.52 | 36.63 |
| + B-tree индекс | 7.06 | 35.02 |
| Секционированная | 3.52 | 38.10 |

#### 1.2. Индексы
Создан составной индекс `(order_date, region, amount)`:
- `order_date` — первое поле для фильтрации диапазона
- `region` — второе поле для GROUP BY (избегаем сортировки)
- `amount` — третье поле для covering index (избегаем чтения таблицы)

**Результат:** узкий запрос ускорился в 1.9× (13.52 → 7.06 мс), план изменился с `Parallel Seq Scan` на `Index Scan`. Широкий запрос остался на `Seq Scan` — это правильно, так как он читает 100% данных.

#### 1.3. Секционирование
Создана секционированная таблица `large.orders_partitioned` по месяцам (24 секции за 2 года).

**Partition pruning:** узкий запрос (июнь 2023) читает только одну секцию `orders_p_2023_06`, что дало ускорение в 2× по сравнению с индексом (7.06 → 3.52 мс).

**Проверка равенства:** `EXCEPT ALL` вернул 0 строк для обоих запросов — данные совпадают.

#### 1.4. Выводы
- Индекс эффективен для узких запросов с высокой селективностью
- Секционирование дает дополнительное ускорение за счет отсечения нерелевантных секций
- Широкий запрос не выигрывает от оптимизации — он читает всю таблицу

### 4. MVCC и механизмы PostgreSQL
#### 4.1. Опыт двух сессий
Терминал 1:
BEGIN;
UPDATE large.orders SET amount = 999.99 WHERE order_id = 101;
-- транзакция открыта

Терминал 2:
SELECT order_id, amount FROM large.orders WHERE order_id = 101;
-- Результат: 189.83 (старое значение)
После COMMIT в Терминале 1, Терминал 2 видит новое значение 999.99.

#### 4.2. Объяснение механизмов
MVCC (Multi-Version Concurrency Control):
При UPDATE PostgreSQL создает новую версию строки, не удаляя старую. Другие транзакции видят старую версию до момента COMMIT изменяющей транзакции. Это обеспечивает неблокирующее чтение на уровне изоляции Read Committed.
WAL (Write-Ahead Logging):
Все изменения сначала записываются в журнал WAL на диск, затем в файлы данных. Это гарантирует:
- Восстановление после сбоя (Crash Recovery): при перезапуске сервер "проигрывает" WAL
- Физическую репликацию: реплики читают WAL лидера
Почему репликация не заменяет бэкап:
Репликация мгновенно копирует любые изменения, включая ошибочные (DROP TABLE, неправильный UPDATE). Бэкап — это "снимок" состояния на момент времени, позволяющий откатить базу назад.
Логическое vs физическое восстановление:
- pg_dump (логический): извлекает SQL-команды, позволяет восстанавливать отдельные таблицы, мигрировать между версиями PostgreSQL
- pg_basebackup + WAL (физический): копирует файлы побайтово, быстрее для больших баз, но требует идентичной архитектуры
Блокировки:
Если бы вторая сессия выполнила UPDATE той же строки, она заблокировалась бы (статус waiting), ожидая завершения первой транзакции. Ожидающие сессии видны в pg_stat_activity (колонка wait_event_type = 'Lock').
